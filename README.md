# eBPF Memory Leak Monitor

This repository implements a memory leak detection tool using eBPF (Extended Berkeley Packet Filter) to trace memory allocations and deallocations in user-space processes. The userspace is implemented in Go using the [cilium/ebpf](https://github.com/cilium/ebpf) library.

## Overview

This project monitors memory allocations and frees by attaching uprobes to libc memory functions (`malloc`, `free`, `calloc`, `realloc`, etc.) and kernel tracepoints for kernel memory operations. It tracks allocation statistics and identifies potential memory leaks by maintaining maps of active allocations and aggregated statistics.

Collected/visible data includes:
- Per-allocation tracking with size, timestamp, and stack trace ID
- Aggregated statistics by stack trace (total size, number of allocations)
- Support for both userspace (libc) and kernel memory tracing
- Configurable filters for allocation size, sample rate, and process targeting

**Note**: The current implementation does not resolve kernel stack traces to human-readable symbols. Stack trace IDs are provided but symbol resolution is not implemented.

## Key Features

- **Userspace Language**: Go instead of C
- **BPF Library**: [cilium/ebpf](https://github.com/cilium/ebpf) instead of libbpf
- **Attach Types**: 
  - uprobes/uretprobes on libc memory functions
  - Kernel tracepoints for kmalloc/kfree operations
- **Code Generation**: Uses `bpf2go` for generating Go bindings from eBPF C code
- **Modern API**: Leverages Go's type safety and error handling
- **Real-time Monitoring**: Continuous reporting of allocation statistics

## Requirements

- Linux kernel 4.1+ with uprobe support
- Linux kernel 4.7+ for tracepoint support
- Go 1.19+
- `clang` and `llvm` for compiling eBPF programs
- Root privileges (or CAP_BPF + CAP_PERFMON) to load eBPF programs
- Target process must be dynamically linked to libc

## Installation

```bash
# Clone the repository
git clone https://github.com/phamnam1805/ebpf-memleak.git
cd ebpf-memleak

# Install dependencies
go mod download

# Build: the Makefile compiles the eBPF C code and builds the Go binary
make build
```

If your environment doesn't use the Makefile, generate Go bindings from the C sources with `bpf2go` and compile the Go program:

```bash
# Generate BPF bindings
go generate ./...

# Build the binary
go build -o ebpf-memleak ./cmd
```

## Usage

Run the memory leak monitor (requires root and a target PID):

```bash
# Monitor a specific process
sudo ./ebpf-memleak -pid 1234

# Monitor with size filters
sudo ./ebpf-memleak -pid 1234 -min-size 1024 -max-size 1048576

# Enable all allocation tracing with kernel tracing
sudo ./ebpf-memleak -pid 1234 -trace-all 

# Monitor with sampling (every 10th allocation)
sudo ./ebpf-memleak -pid 1234 -sample-rate 10
```

### Command Line Flags

The following flags are supported:

- `-pid` (required): Process ID to monitor for memory leaks
- `-min-size`: Minimum allocation size to trace (default: 0)
- `-max-size`: Maximum allocation size to trace (default: unlimited)
- `-page-size`: Page size for memory calculations (default: 4096)
- `-sample-rate`: Sample every Nth allocation (default: 1, trace all)
- `-trace-all`: Enable verbose tracing of all allocations (boolean)
- `-wa-missing-free`: Workaround for missing free events (boolean)

### Understanding the Output

The output shows that the program detected malloc calls from **3 different locations** in the `test_memleak` program, each creating memory leaks:

**1. `leak_with_loop` function - 10240 bytes in 5 allocations:**
```c
// This function calls malloc() 5 times in a loop, each allocating 2048 bytes
void leak_with_loop() {
    for (int i = 0; i < 5; i++) {
        malloc(2048);  // Never freed - causes memory leak
    }
}
```

**2. `leak_large` function - 8192 bytes in 1 allocation:**
```c
// This function allocates a large chunk of memory
void leak_large() {
    malloc(8192);  // Never freed - causes memory leak
}
```

**3. `leak_small` function - 1024 bytes in 1 allocation:**
```c
// This function allocates a small chunk of memory
void leak_small() {
    malloc(1024);  // Never freed - causes memory leak
}
```

**How Detection Works:**
- **Stack Trace Capture**: When malloc() is called, the eBPF program captures the complete call stack
- **Grouping by Origin**: Allocations are grouped by their stack trace, so all calls from the same function appear together
- **Leak Detection**: Memory allocated but never freed shows up as "outstanding allocations"
- **Symbol Resolution**: Function names like `leak_with_loop+0x12` show the exact location in your code

**Memory Leak Indicators:**
- **Outstanding allocations**: Memory that was allocated but never freed
- **Growing totals**: Numbers increase over time for active leaks
- **Stack traces**: Show exact location where leaks originate

## How It Works

### Kernel-Side (eBPF)

The eBPF program attaches to multiple points:

1. **Userspace Memory Functions** (via uprobes):
   - `malloc`, `calloc`, `realloc` (entry and exit)
   - `free` (entry only)
   - `posix_memalign`, `aligned_alloc`, `valloc`, `memalign`, `pvalloc`

2. **Kernel Memory Tracepoints**:
   - `kmem:kmalloc`, `kmem:kmalloc_node`
   - `kmem:kfree`
   - `kmem:kmem_cache_alloc`, `kmem:kmem_cache_free`
   - `kmem:mm_page_alloc`, `kmem:mm_page_free`
   - `percpu:percpu_alloc_percpu`, `percpu:percpu_free_percpu`

For each allocation event:
- Records allocation size, timestamp, and captures stack trace
- Updates per-allocation tracking in the `allocs` map
- Aggregates statistics by stack ID in the `combined_allocs` map
- Applies size and sampling filters

### User-Space (Go)

1. **Initialization**: Parse CLI flags and validate required parameters
2. **BPF Loading**: Load eBPF object and set configuration variables
3. **Attachment**: Attach uprobes to libc functions and kernel tracepoints
4. **Monitoring**: Continuously read BPF maps and report statistics
5. **Cleanup**: Properly detach and close BPF objects on shutdown

The userspace component uses a min-heap data structure for efficient top-N allocation tracking and provides real-time statistics aggregation.

## Limitations

- **Stack Trace Resolution**: Kernel stack traces are captured as IDs but not resolved to human-readable symbols
- **Symbol Resolution**: Userspace stack trace symbolization is limited
- **Performance Impact**: Tracing all allocations can impact performance; use sampling for production
- **libc Dependency**: Target processes must use standard libc memory functions

## Troubleshooting

- **"Failed loading probe objects"**: Ensure you're running as root and have required kernel features
- **"Failed to attach uprobe"**: Verify the target process is running and uses dynamic libc
- **"Invalid argument (MaxEntries may be incorrectly set to zero)"**: BPF map configuration issue - try regenerating with `make generate`
- **High CPU usage**: Reduce sampling rate or increase size filters to reduce trace volume

## Use Cases

- **Memory Leak Detection**: Identify allocations that are never freed
- **Memory Usage Analysis**: Understand allocation patterns and hotspots
- **Performance Debugging**: Find excessive memory allocation locations
- **Production Monitoring**: Track memory usage trends in running applications
